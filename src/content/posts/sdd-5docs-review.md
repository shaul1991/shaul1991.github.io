`review.md`는 작업이 끝난 뒤 붙이는 요약문이 아니라 완료 판정의 게이트다. 어떤 작업을 했고 어떤 경우를 검수했는지 실제 내용이 적히기 전에는 완료라고 선언하지 않는다. 파일이 존재해도 스캐폴딩의 자리표시자 상태라면 미작성이다.

## 핵심부터

`review.md`에는 최소한 다음 사실을 다시 찾을 수 있어야 한다.

- 실제로 바뀐 것과 의도적으로 바꾸지 않은 것.
- spec의 수락 조건마다 대응하는 검증 증거.
- 테스트뿐 아니라 실제 실행에서 관찰한 결과.
- 자기검증에서 발견해 고친 결함.
- 충족하지 못한 조건과 남은 위험.
- 이 작업 중 LocalMind에 남긴 결정 기록의 연결점.

목차와 형식을 고정하는 것이 목적은 아니다. 다음 사람이 완료 주장을 재검증할 수 있을 만큼 구체적이어야 한다.

## 테스트 green만으로 닫지 않는다

테스트는 중요한 증거지만 테스트가 실제 문제를 잡는지 먼저 확인해야 한다. 새 테스트라면 구현 전에 실패하는 것을 보고, 수정 후 같은 조건에서 통과하는지 확인한다.

그 뒤 실제 실행을 관찰한다. 웹 화면이라면 목표 뷰포트에서 잘림과 오버플로를 보고, 배포 작업이라면 원격 상태를 확인한다. review에는 "확인함" 대신 어떤 환경에서 무엇을 실행했고 어떤 결과를 봤는지 적는다.

## 수락 조건과 증거를 다시 연결한다

구현 중에는 tasks를 따라가지만 완료 때는 다시 `spec.md`로 올라간다. 각 수락 조건에 테스트, 실측, 실행 관찰 중 하나 이상의 증거가 대응하는지 확인한다.

tasks가 모두 체크돼도 수락 조건 하나가 비어 있으면 완료가 아니다. 반대로 구현 과정에서 요구가 잘못됐다는 근거가 생겼다면 코드를 억지로 맞추지 않고 spec 변경과 그 이유를 남긴다.

## 결함을 찾는 검토를 한 번 더 거친다

작성자는 자신의 구현 의도를 알고 있어서 같은 맹점을 반복하기 쉽다. 가능하면 구현 문맥과 분리된 AI에게 적대적 검토를 맡긴다. 독립 검토를 쓸 수 없다면 같은 세션에서 결함을 찾는 관점으로 다시 읽고, 비독립 검토였다는 사실을 적는다.

발견한 문제를 고쳤다면 변경된 결과를 다시 검증한다. 이전 실행의 green을 새 코드에 그대로 물려주지 않는다.

## 미충족을 숨기지 않는 것이 완료의 일부다

권한, 외부 서비스, 환경 제약 때문에 확인하지 못한 조건은 미충족 또는 미검증으로 남긴다. 추정한 성공보다 검증하지 못했다는 기록이 다음 작업에 더 유용하다.

작업 중 생긴 중요한 트레이드오프는 LocalMind에 남기고, review에서 그 기록을 다시 찾을 수 있게 연결한다. 다음 AI는 저장소의 다섯 문서로 현재 결과를 이해하고 LocalMind에서 결정의 이유를 소환한다.

이렇게 `review.md`가 채워져야 goal에서 시작한 질문이 실제 결과와 증거로 닫힌다.
