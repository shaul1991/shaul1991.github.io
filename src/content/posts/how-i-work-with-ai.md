LocalMind에 남아 있는 기록을 다시 찾아보니, 프로젝트와 도구는 달라도 반복해서 등장하는 방식이 있었다. 먼저 목표와 완료 조건을 정한다. 구현은 작게 나누고, 결과는 말이 아니라 실행된 증거로 확인한다. 판단이 필요한 지점에서는 선택지와 트레이드오프를 드러내고, 마지막 결정은 내가 한다.

처음부터 이 흐름을 완성된 방법론으로 만든 것은 아니다. AI에게 일을 많이 맡길수록 결과를 만드는 속도보다 결과를 믿을 수 있는지가 더 큰 문제가 됐다. 그때마다 규칙을 하나씩 보탰고, 너무 느려진 규칙은 다시 줄였다. 지금의 흐름은 그 시행착오가 남긴 현재 답안이다.

## 요청을 바로 구현하지 않는다

아이디어를 말하는 것과 구현할 작업을 정의하는 것은 다르다. "이 기능을 만들어 보자"는 시작점일 뿐이다. 나는 먼저 이 요청이 해결하려는 문제, 이번 작업의 범위, 결과물이 놓일 위치, 완료했다고 판단할 조건을 정리한다.

완료 조건은 가능한 한 관찰할 수 있게 쓴다. "모바일을 개선한다"보다 "390px 화면에서 메뉴가 겹치지 않고 가로 오버플로가 없어야 한다"가 낫다. "검색을 고친다"보다 어떤 입력에서 어떤 결과가 나와야 하는지 적는 편이 낫다. 이 조건이 있어야 AI도 구현 방향을 고를 수 있고, 나도 결과를 검수할 수 있다.

모호함이 결과를 바꿀 정도라면 구현 전에 질문한다. 여러 해석이 가능한데도 조용히 하나를 고르는 것은 빠른 진행처럼 보이지만, 대개 나중에 더 큰 수정으로 돌아온다. 반대로 결과가 거의 달라지지 않는 사소한 선택까지 모두 묻지는 않는다. 질문에도 비용이 있기 때문이다.

## 조사와 계획은 문서의 양이 아니라 판단의 질을 위한 것이다

새로운 구조나 되돌리기 어려운 선택이 들어가면 먼저 조사한다. 이때 조사 결과를 길게 모으는 것보다 어떤 결정을 내려야 하는지부터 정한다. 필요한 질문, 확인할 근거, 아직 사실로 볼 수 없는 가정을 구분한다.

그다음 조사 결과를 작업 구조로 바꾼다. 범위, 완료 조건, 작업 단위, 검증 방법이 여기서 나온다. 계획은 구현을 대신하는 문서가 아니다. 구현 중 무엇이 달라졌는지 알아차리기 위한 기준선에 가깝다.

나는 계획을 절대적인 명령으로 취급하지 않는다. 실제 코드를 확인했을 때 전제가 틀렸다면 계획을 고친다. 다만 왜 바뀌었는지는 남긴다. 계획에서 조용히 이탈하면 결과가 좋아도 다음 사람이 그 이유를 알 수 없다.

## 작업 크기에 맞게 절차를 줄이고 늘린다

모든 작업에 조사, 명세, 계획, 구현, 리뷰의 전체 절차를 적용하면 안전해 보인다. 하지만 작은 수정에서는 준비 시간이 실제 변경 시간보다 길어질 수 있다.

그래서 변경의 크기와 되돌리기 어려운 정도에 따라 절차를 조절한다. 문구 수정이나 명백한 스타일 오류는 짧은 확인과 직접 검증으로 끝낼 수 있다. 반면 데이터 구조, 인증, 공개 API, 여러 프로젝트에 영향을 주는 규칙은 조사와 명세를 먼저 둔다.

신중함은 모든 작업을 무겁게 만드는 것과 다르다. 간단한 일은 간단하게 처리하되, 틀렸을 때 비용이 큰 일에는 더 많은 근거와 검토를 붙인다. 같은 절차를 항상 반복하는 대신 위험에 맞춰 작업 흐름을 조절하는 편이 실제로 더 안전했다.

## 구현은 테스트 가능한 행동 단위로 나눈다

계획이 정해지면 작업을 한 번에 크게 넘기지 않는다. 사용자가 확인할 수 있는 행동이나 실패 조건을 기준으로 작게 나눈다. 각 단위에는 변경할 대상과 검증 방법이 함께 있어야 한다.

버그를 고칠 때는 가능하면 먼저 실패를 재현한다. 새 기능도 완료 조건을 검사하는 테스트를 먼저 추가한다. 테스트가 실패하는 것을 확인한 뒤 구현하고, 통과하면 빌드와 실제 화면까지 확인한다. 모든 작업을 테스트 코드로 표현할 수는 없지만, 무엇으로 성공을 판정할지는 구현 전에 정할 수 있다.

이 방식은 AI가 코드를 많이 생성하는 상황에서 특히 중요하다. 코드의 양은 진행률이 아니다. 테스트 가능한 행동 하나가 끝났고, 그 결과를 직접 확인했을 때 비로소 작업이 앞으로 움직였다고 본다.

## AI에게 실행을 맡기되 판단까지 넘기지는 않는다

AI는 조사 범위를 넓히고, 여러 선택지를 비교하고, 반복적인 구현과 검증을 수행하는 데 강하다. 필요하면 역할도 나눈다. 한 에이전트가 구현하고 다른 에이전트가 독립된 맥락에서 검토하게 할 수 있다. 조사 결과를 작업 구조로 바꾸는 역할과, 다음 작업자가 이어받을 수 있도록 결과를 정리하는 역할도 분리한다.

그래도 Supervisor는 항상 사람이다. 리뷰어의 의견은 중요한 근거지만 자동 승인 버튼은 아니다. 무엇을 반영할지, 위험을 받아들일지, 지금 머지할지는 사람이 최종 결정한다.

이 구분이 있어야 자율성을 높일 수 있다. AI의 행동을 하나하나 제한하면 능력이 좋아져도 얻는 이득이 작다. 대신 결과를 평가하는 기준을 강하게 둔다. 목표와 명세를 충족했는지, 테스트가 통과하는지, 회귀가 없는지, 실제 산출물이 제대로 동작하는지를 본다.

## 완료는 설명이 아니라 증거로 판단한다

에이전트가 "완료했다"고 말한 것은 완료의 증거가 아니다. 나는 가능한 한 실제 산출물을 다시 확인한다.

코드 작업이라면 테스트, 타입 검사, 빌드, diff, CI 결과를 확인한다. 화면 작업이라면 데스크톱과 모바일에서 직접 렌더링하고, 텍스트 잘림과 겹침, 가로 오버플로, 접근성 상태를 본다. 외부 링크를 추가했다면 최종 DOM의 주소와 접근 가능한 이름도 확인한다.

구현 직후에는 self-review로 한 번 더 닫는다. 처음부터 다시 읽는 독립 리뷰가 명세 누락과 회귀를 찾는다. 이 단계에서 문제가 나오면 완료를 미루고 다시 구현한다. 리뷰 횟수를 채우는 것이 목적은 아니다. 새로 발견되는 문제가 사라지고 완료 조건을 만족했을 때 멈춘다.

## 모든 결정을 기록하지는 않는다

사소한 변수명이나 자명한 수정까지 기록하면 중요한 판단이 묻힌다. 나는 다음과 같은 경우를 주로 남긴다.

- 아키텍처나 기술처럼 되돌리기 어려운 선택
- 두 선택지 사이의 명시적인 트레이드오프
- 다른 프로젝트나 사람에게 영향을 주는 결정
- 조사 끝에 어떤 대안을 채택하거나 기각한 경우

기록에는 무엇을 선택했는지만 적지 않는다. 왜 선택했는지, 어떤 전제를 두었는지, 검토했지만 버린 대안은 무엇인지 함께 남긴다. 상세 명세가 이미 있다면 결정 노트는 그것을 복제하지 않는다. 나중에 "왜 그렇게 정했지?"라고 물었을 때 원문으로 돌아갈 수 있는 짧은 지도 역할을 한다.

LocalMind는 이 지도를 다시 찾는 데 사용한다. 다음 작업을 시작할 때 관련 결정과 전제를 먼저 불러오고, 이번 작업에서 새로 생긴 의미 있는 판단을 다시 기록한다. 기록의 목적은 과거를 보관하는 데 그치지 않는다. 다음 의사결정의 출발점을 조금 앞으로 옮기는 것이다.

## 작업을 끝낼 때 다음 시작점도 만든다

작업이 끝나면 변경 파일과 테스트 결과만 남기지 않는다. 무엇을 했는지, 어떤 결정을 내렸는지, 아직 남은 위험과 후속 작업은 무엇인지 정리한다. 다음 사람이 같은 조사를 반복하지 않도록 하기 위해서다. 며칠 뒤의 나도 그 "다음 사람"에 포함된다.

실패도 같은 방식으로 다룬다. 도구가 실패했거나 가정이 틀렸다면 성공한 결과만 남기지 않는다. 어떤 경로가 막혔고 무엇으로 우회했는지 기록한다. 반복해서 나타나는 패턴은 규칙이나 재사용 가능한 작업 방법으로 바꾼다.

내가 지향하는 학습 흐름은 단순하다. 작업을 관찰하고, 반복되는 문제를 돌아보고, 유용한 교훈을 규칙이나 도구에 반영한 뒤, 다음 작업에서 다시 사용한다. 자동으로 모든 것을 바꾸지는 않는다. 제안과 근거를 보고 사람이 채택할 때만 작업 방식이 바뀐다.

## 지금의 작업 흐름

현재 흐름을 한 줄로 줄이면 이렇다.

```text
요청
→ 문제·범위·완료 조건 정리
→ 필요한 만큼 조사
→ 작업 크기에 맞는 계획
→ 테스트 가능한 단위로 구현
→ 테스트·빌드·실제 화면 검증
→ self-review와 PR·CI
→ 사람이 최종 결정
→ 중요한 결정과 후속 작업을 LocalMind에 기록
```

이 흐름은 고정된 의식이 아니다. 작은 작업에는 줄이고, 위험한 작업에는 더한다. 사용하는 AI나 프로젝트 관리 도구가 바뀌어도 목표, 근거, 검증, 사람의 최종 판단이라는 뼈대는 유지한다.

AI와 함께 일하면서 내가 직접 쓰는 코드의 비중은 앞으로 더 줄어들 수 있다. 대신 어떤 문제를 풀지 정하고, 무엇을 사실로 받아들일지 판단하고, 결과가 충분한지 확인하는 일의 비중은 커질 것이다. 지금의 작업 흐름은 그 변화에 대비하기 위해 만든 나의 운영 방식이다.
