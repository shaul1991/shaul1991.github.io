대화형 AI에게 “이 문서를 요약해 줘”라고 묻는 것과, 내 컴퓨터의 문서를 찾아 읽고 결과를 파일로 저장한 뒤 다음 날 텔레그램으로 보내게 하는 것은 다른 문제다. 후자에는 답을 생성할 모델뿐 아니라 파일 접근, 명령 실행, 권한 확인, 작업 상태 저장, 예약 실행과 메시지 전달이 필요하다.

Hermes Agent는 이 실행 계층을 맡는 오픈 소스 에이전트 런타임이다. 특정 모델 하나를 새로 만드는 제품이 아니라, 선택한 언어 모델에 도구와 지속 상태, 실행 환경, 사용자 인터페이스를 연결한다. 공식 문서는 Hermes를 IDE에 묶인 코딩 보조나 단일 API의 챗봇 래퍼가 아니라, 노트북·서버·컨테이너 등 사용자가 정한 환경에서 동작하는 에이전트로 설명한다.[1]

이 글은 설치 전에 필요한 개념을 먼저 정리한다. Hermes가 일반적인 채팅 서비스와 무엇이 다른지, ChatGPT 구독은 어디에 연결되는지, 메모리·스킬·세션·프로필은 어떻게 구분되는지 이해하면 이후 설치와 텔레그램 연동에서 무엇을 설정하는지 훨씬 분명해진다.

## 핵심

Hermes Agent를 한 문장으로 줄이면 **모델이 판단한 일을 실제 환경에서 수행하고, 그 결과를 다시 모델과 사용자에게 돌려주는 실행 시스템**이다.

```text
터미널 · Desktop · 텔레그램 · 예약 작업
                    │
                    ▼
             Hermes Agent
       문맥 구성 · 세션 · 권한 · 도구 배정
                    │
          ┌─────────┴─────────┐
          ▼                   ▼
     모델/provider        실행 도구
   다음 행동을 판단     파일 · 터미널 · 웹 · 브라우저
          │                   │
          └─────────결과──────┘
                    │
             검증 후 응답·전달
```

모델이 파일을 직접 만지는 것은 아니다. Hermes가 모델에 사용 가능한 도구의 형태를 알려주고, 모델이 도구 호출을 요청하면 Hermes가 이를 실행해 결과를 다시 대화 흐름에 넣는다. 이 반복이 끝나야 최종 답변이 만들어진다. 공식 도구 목록에는 파일 편집, 터미널, 웹 검색, 브라우저 자동화, 메모리, 예약 작업과 하위 에이전트 위임 등이 포함되며, 터미널은 로컬·Docker·SSH·클라우드 샌드박스 같은 여러 실행 환경을 선택할 수 있다.[2]

따라서 “답을 잘 쓰는가”는 주로 모델의 역량이고, “어디에서 어떤 도구를 어떤 권한으로 실행하며 결과를 어떻게 남기는가”는 Hermes 구성의 영역이다.

## Hermes를 이루는 여섯 부분

| 구성 요소 | 하는 일 | 사용자가 정하는 것 |
| --- | --- | --- |
| 모델과 provider | 요청을 해석하고 다음 행동을 판단한다 | 사용할 서비스, 모델, 인증 방식, fallback |
| 에이전트 루프 | 문맥을 구성하고 모델 호출과 도구 결과를 이어 붙인다 | 세션과 컨텍스트 설정 |
| 도구와 실행 backend | 파일·명령·웹·브라우저 등 실제 동작을 수행한다 | 활성 도구, 작업 폴더, local·Docker·SSH 등 실행 위치 |
| 메모리와 스킬 | 장기 사실과 재사용 절차를 다음 작업에 활용한다 | 무엇을 기억하고 어떤 절차를 설치할지 |
| 게이트웨이와 cron | 메신저 요청을 받고 예약 작업을 실행·전달한다 | 연결 플랫폼, 허용 사용자, 실행 주기 |
| 프로필 | 목적별 설정과 상태를 분리한다 | 개인용·업무용·개발용 에이전트의 경계 |

이 구조 덕분에 같은 Hermes라도 사용 방식은 크게 달라진다. 노트북의 개발 도우미가 될 수도 있고, 서버에서 텔레그램 요청을 기다리는 개인 비서가 될 수도 있으며, Docker 안에서 정해진 작업만 수행하는 자동화 에이전트가 될 수도 있다.

## ChatGPT나 코딩 에이전트와 무엇이 다른가

세 제품군의 경계가 완전히 고정돼 있는 것은 아니다. ChatGPT도 파일 분석과 예약 기능을 제공하고, 코딩 에이전트도 세션 저장과 원격 작업을 지원한다. 다음 표는 기능의 유무보다 **기본 운영 중심**을 비교한 것이다.

| 구분 | 일반적인 중심 | 실행 환경 | 지속 운영과 채널 확장 |
| --- | --- | --- | --- |
| ChatGPT 같은 호스팅 채팅 서비스 | 제공사가 만든 앱에서 대화와 콘텐츠 생성 | 서비스가 제공하는 도구·샌드박스 | 제공되는 기능과 채널 범위 안에서 사용 |
| Codex CLI·Claude Code 같은 코딩 에이전트 | 저장소 탐색, 코드 수정, 테스트와 개발 흐름 | 주로 로컬 또는 원격 개발 환경 | 제품별 세션·자동화 기능을 사용 |
| Hermes Agent | 여러 모델과 도구를 묶은 자가 운영 에이전트 | local·Docker·SSH·클라우드 backend를 선택 | 게이트웨이, cron, 프로필을 직접 구성 |

Hermes의 장점은 “모든 면에서 더 똑똑하다”가 아니다. **모델과 실행 환경, 도구, 접속 채널을 한 제품의 기본값에 묶지 않고 조합할 수 있다**는 점이다. 반대로 사용자가 인증, 권한, 상주 프로세스와 업데이트를 관리해야 한다는 책임도 생긴다.

## ‘ChatGPT 연동’이 뜻하는 것

Hermes와 ChatGPT를 연결한다고 해서 `chatgpt.com`의 대화 화면을 Hermes 안에 넣거나 기존 ChatGPT 대화를 자동으로 가져오는 것은 아니다. Hermes가 지원하는 모델 provider 중 하나로 OpenAI Codex 인증을 선택하는 구조다.

공식 provider 문서 기준으로 `hermes model`에서 **ChatGPT or Codex Subscription**을 선택하면 기기 코드 OAuth로 로그인하고 Codex 계열 모델을 사용할 수 있다. 별도의 OpenAI API 키나 Codex CLI 설치는 필수가 아니다.[9] 다만 어떤 ChatGPT 요금제가 대상인지, Hermes 사용량이 구독 한도에 어떻게 계산되는지에 대한 세부 정책은 공식 문서에 완전히 명시돼 있지 않다. 구독 인증과 API 종량제 인증을 같은 것으로 가정하지 않는 편이 안전하다.[9]

역할을 나누면 다음과 같다.

```text
ChatGPT/Codex 구독 인증 → 모델을 사용할 권한
Hermes Agent            → 문맥·도구·세션·실행을 관리
macOS 또는 서버          → 실제 파일과 명령이 동작하는 환경
텔레그램                 → 요청과 결과가 오가는 접점
```

이 구분을 알고 있으면 장애도 층별로 볼 수 있다. 로그인에 실패하면 provider 인증을, 파일이 만들어지지 않으면 도구와 권한을, 텔레그램에서만 답이 없으면 게이트웨이와 봇 설정을 확인하면 된다.

## 세션, 메모리, 스킬은 서로 다르다

Hermes의 “기억”을 하나의 기능으로 보면 운영 중 혼란이 생긴다.

| 종류 | 저장하는 것 | 예시 |
| --- | --- | --- |
| 세션 | 한 대화의 메시지와 도구 실행 흐름 | 방금 수정한 파일, 이번 질문의 앞뒤 맥락 |
| 메모리 | 다음 세션에도 유효한 짧고 선별된 사실 | 선호 언어, 프로젝트 규칙, 환경 특성 |
| 스킬 | 특정 일을 반복하는 절차와 참고 자료 | PR 검토 순서, PDF 표 추출법, 배포 점검표 |

공식 메모리는 용량이 제한된 `MEMORY.md`와 `USER.md`에 선별된 사실을 보존하고, 새 세션 시작 시 문맥에 넣는다. 원시 로그나 임시 상태를 무제한 저장하는 데이터베이스와는 목적이 다르다.[3]

스킬은 필요할 때만 불러오는 절차 문서다. 일반적인 대화에는 싣지 않다가 관련 작업에서 로드하므로, 긴 사용법을 매번 프롬프트에 붙이지 않고 재사용할 수 있다. Hermes는 설치된 스킬을 slash command나 자연어 요청에서 사용할 수 있고, 작업 중 발견한 절차를 새 스킬로 만들거나 기존 스킬을 개선할 수도 있다.[4]

그래서 공식 문서가 말하는 “학습”은 모델 가중치를 계속 재훈련한다는 뜻이 아니다. 경험에서 선별한 사실을 메모리에 남기고, 성공한 절차를 스킬로 구조화해 다음 작업에서 재사용하는 닫힌 루프에 가깝다.[1][3][4]

## 게이트웨이가 에이전트를 메신저로 데려온다

CLI를 닫은 뒤에도 외부 요청을 받으려면 게이트웨이를 백그라운드 서비스로 실행해야 한다. 그러면 Hermes는 텔레그램·디스코드·슬랙 등에서 새 메시지를 기다릴 수 있다. 게이트웨이는 플랫폼별 메시지를 세션에 연결하고 에이전트에 전달하며, cron 스케줄러와 결과 전송도 함께 맡는다.[5]

```text
텔레그램 메시지
      ↓
플랫폼 adapter → 사용자 허용 여부 확인 → 채팅별 세션
      ↓
Hermes Agent → 모델 판단 → 도구 실행
      ↓
같은 텔레그램 대화로 결과 전달
```

cron은 일회성 또는 반복 작업을 새 에이전트 세션에서 실행하고, 결과를 로컬이나 설정된 메시징 채널로 보낼 수 있다.[7] 예를 들어 매일 아침 공개 피드를 읽어 요약하거나, 서버 상태를 확인해 이상이 있을 때만 알리는 흐름을 만들 수 있다. 다만 예약 작업은 사람이 화면 앞에 없는 상태에서 실행되므로 provider 비용, credential 만료, 위험 명령 승인 정책과 전달 대상을 별도로 설계해야 한다.

## 프로필은 역할을 나누지만 샌드박스는 아니다

개인 메모와 회사 프로젝트, 연구용 도구와 운영용 credential을 한 에이전트에 모두 넣으면 문맥과 권한이 섞인다. Hermes 프로필은 각각 별도의 설정, API 키, 메모리, 세션, 스킬, cron 작업과 게이트웨이 상태를 갖는다.[6]

예를 들어 `personal`, `work`, `research` 프로필을 만들면 각 에이전트의 성격과 기록을 분리할 수 있다. 그러나 프로필은 상태 분리이지 파일 접근 차단이 아니다. 기본 local backend에서는 모두 현재 macOS 사용자 권한으로 파일에 접근할 수 있다. 실제 격리가 필요하면 별도 OS 계정, Docker·원격 sandbox, 제한된 작업 디렉터리와 credential을 함께 사용해야 한다.[2][6]

## 권한을 준 만큼만 안전하다

에이전트가 파일을 읽고 명령을 실행할 수 있다는 것은 생산성과 위험이 같은 통로를 쓴다는 뜻이다. Hermes는 허용 사용자 확인, 위험 명령 승인, 파일 쓰기 제한, 컨테이너 격리와 세션 분리 같은 여러 안전 계층을 제공한다.[8] 하지만 이것이 모든 실수를 자동으로 막는다는 뜻은 아니다.

처음에는 다음 원칙이 현실적이다.

1. **연습 폴더에서 시작한다.** 홈 전체나 중요한 저장소를 첫 작업 범위로 주지 않는다.
2. **필요한 도구만 켠다.** 파일 생성 확인에 브라우저 제어와 전체 디스크 접근은 필요 없다.
3. **위험 명령 승인을 유지한다.** 편의를 위해 `--yolo`를 기본값으로 만들지 않는다.
4. **비밀 값은 대화와 로그에 붙이지 않는다.** API 키와 봇 토큰은 전용 credential 저장소에 둔다.
5. **결과를 외부에서 다시 확인한다.** “완료했다”는 문장보다 실제 파일, 테스트 결과와 서비스 상태를 본다.
6. **상시 실행은 더 좁게 구성한다.** cron과 메신저 봇에는 허용 사용자, 비용 한도와 실패 알림을 둔다.

## 어떤 일에 잘 맞을까

Hermes는 한 번의 답변보다 **여러 도구와 상태가 이어지는 작업**에서 차이가 커진다.

- 저장소를 읽고 코드를 수정한 뒤 테스트 결과까지 확인하는 개발 작업
- 여러 웹 자료를 수집하고 출처가 있는 문서나 표로 정리하는 조사
- 정기적으로 공개 피드나 서비스 상태를 확인해 메시지로 전달하는 자동화
- 반복 업무를 스킬로 남기고 다음 세션에 같은 절차를 재사용하는 개인 워크플로
- 개인용·업무용·연구용 에이전트를 프로필로 나누어 운영하는 구성

반대로 단순한 질문 한두 개에 답을 받는 것이 목적이라면 호스팅 채팅 서비스가 더 간단할 수 있다. Hermes를 운영한다는 것은 모델 선택만이 아니라 실행 위치, 권한, 지속 상태와 업데이트까지 직접 책임진다는 뜻이다.

다음 글에서는 Apple Silicon Mac에 Hermes를 설치하고, 모델 응답과 파일 도구를 실제 결과로 확인한 뒤 필요할 때만 launchd 게이트웨이를 상주시킨다. 이후 ChatGPT 구독 인증과 텔레그램 연결을 각각 독립된 단계로 이어갈 예정이다.
